## Overview

MIX is a **compiled, statically-typed systems language** — lexer, parser, semantic analyzer, and LLVM backend — built from the ground up with **zero prior compiler or language implementation experience**. Every line of the compiler, every pass in the pipeline, and every design decision was generated by AI under the direction of someone who had never written a lexer, walked an AST, or thought about instruction selection before starting.

The entire project was built through **AI pair programming** — describing what the language should do, sketching the architecture, getting feedback, reviewing generated code line-by-line, fixing bugs, and refining. The AI didn't build MIX on its own; it was guided through directed prompting and careful review.

The compiler is written in **C** (~7,500 lines) and produces native binaries through **LLVM** (primary backend) with a **C backend** as a portability fallback. There's an LSP server, a code formatter (`mix fmt`), a C header binding generator (`--bind`), DWARF debug info, and a standard library — all built the same way.

## Architecture

MIX is organized as a classic multi-stage compiler pipeline:

```text
source.mix → Lexer → Parser → Sema (type check + symbol resolution)
    → Lower → LLVM backend (.ll) → clang -c → .o → link → binary
                                                        ↑
                                              lib/runtime.c
```

Each stage feeds into the next with no intermediate IR beyond the AST and the lowered representation:

```text
src/
├── main.c            # CLI driver + multi-module pipeline
├── mix.h             # Shared types and version
├── arena.h/c         # Arena allocator
├── errors.h/c        # Error reporting (colored, source-annotated)
├── token.h           # Token definitions
├── lexer.h/c         # Character-by-character tokenizer
├── ast.h/c           # AST node definitions + printer
├── parser.h/c        # Recursive descent parser (Pratt for expressions)
├── types.h/c         # Type system (shapes, generics, optionals, etc.)
├── symtab.h/c        # Scoped symbol table
├── sema.h/c          # Semantic analysis (type inference, validation)
├── lower.h/c         # Lowering from AST to LIR
├── lir.h/c           # Lowered IR representation
├── llvm_emit.h/c     # LLVM IR emitter (primary backend)
├── c_emit.h/c        # C backend (portability fallback)
├── cbind.h/c         # C header binding generator
├── fmt.h/c           # Code formatter
└── lsp/              # Language server protocol implementation
```

**~7,500 lines of C.** The runtime is another ~750 lines in `lib/runtime.c`.

## The Language

MIX is a systems language with the footprint of C and the clarity of a modern language. It draws inspiration from **C** (performance, simplicity), **Python** (readability, indentation-sensitive syntax), and **Odin** (explicit design, `defer`, ergonomic C interop). The goal was an elegant, modern language that's easy to read and write — without sacrificing C-level speed.

It compiles to native code — no VM, no GC, no runtime overhead. Memory is managed through zones (region-based allocation) with explicit borrows (`ref`/`ref!`) and boxes (`Box[T]`) for stable addresses.

### Variables

```rust
x = 42          // immutable
x! = 42         // mutable — ! marks mutability
x! += 1         // mutation
```

No `let`, `var`, `const`, `val`. Immutable by default, mutable by explicit `!`.

### Shapes (Structs with Methods)

```rust
shape Vec2
    x, y: float

    +(other: Vec2) -> Vec2              // operator overloading
        Vec2(x: x + other.x, y: y + other.y)

    area() -> float                     // computed field (no parens needed)
        x * y
```

Construction uses named fields: `Vec2(x: 1.0, y: 2.0)`. Methods live inside the shape. Operator overloading uses the operator as the method name.

### Generics

```rust
@T
first(list: [T]) -> T?
    if list.len == 0
        none
    else
        list[0]

@T has +
sum(list: [T]) -> T
    list.fold(init: 0, fn: (a, b) => a + b)
```

Type parameters use `@T` syntax. `has` constraints check for operators and methods at call sites.

### Control Flow

```rust
if score > 90
    "A"
else if score > 80
    "B"
else
    "C"

for i in 0..10           // range (exclusive end)
    print(i)

for i in 0..=10          // range (inclusive end)
    print(i)

for item in list         // for-each
    process(item)

for item! in list        // mutable for-each
    item = modify(item)

while running
    tick!()
```

### Functions

```rust
// Pure — no side effects
add(a, b)
    a + b

// Side effects — marked with ~
greet(name) ~
    print("Hello {name}!")

// Mutates arguments — marked with !
increment(n) !
    n! += 1

// Lambda
double = x => x * 2
apply(double, 5)        // 10
```

Last expression is the return value. `done` for early exit.

### Optionals & Error Handling

```rust
// Optional: T?
find(list: [int], val: int) -> int?
    for x in list
        if x == val
            done x
    none

val = find(nums, 7) else 0       // default on none
val = find(nums, 7)?              // propagate

// Error handling through ~ functions with fail
read(path: str) -> str ~
    f = open!(path) else
        fail "could not open"
    f.read!()

data = read("file.txt") else "default"      // fallback
```

### Concurrency

```rust
go fetch_data("url")                    // fire and forget
result = wait go compute(data)          // spawn and await

counter! = shared int(0)                // thread-safe shared value
counter.update!(v => v + 1)            // automatic locking
x = counter.read()
```

### Zones — Memory Management

MIX uses region-based allocation. No garbage collector, no borrow checker — just explicit lifetimes through zones:

```rust
main() ~
    frame = zone_create("frame", 1024 * 1024)
    points! = List[Vec2].new(frame)

    points.push!(Vec2(x: 1.0, y: 2.0))
    // zone_reset(frame) — frees everything in one shot
    zone_destroy(frame)
```

### String Interpolation

```rust
name = "Alice"
greeting = "Hello {name}!"          // "Hello Alice!"
path = "line one\nline two"        // escape sequences
```

### Slices & Comprehensions

```rust
nums[1..3]          // by range
nums[..2]           // first 2
nums[-3..]          // last 3
[x*x for x in nums]               // comprehension
[x for x in nums if x % 2 == 0]   // filtered
```

### C Interop

MIX treats C as a peer, not a foreign language. There are **two seamless paths** to call C — neither requires writing a binding generator config file or a separate IDL.

#### Path 1: Declare what you need with `extern`

Just write an `extern` block naming the library and declare only the functions you actually use. No header parsing, no build steps, no binding generator:

```rust
extern "SDL3"
    SDL_Init(flags: uint32) -> int32 ~
    SDL_Quit() ~
    SDL_CreateWindow(title: *byte, w: int32, h: int32, flags: uint64) -> *byte ~
    SDL_DestroyWindow(win: *byte) ~
    SDL_PollEvent(event: *byte) -> int32 ~
    SDL_Delay(ms: uint32) ~

main()
    SDL_Init(SDL_INIT_VIDEO)
    win = SDL_CreateWindow("MIX + SDL3", 800, 600, 0)
    // ...
    SDL_DestroyWindow(win)
    SDL_Quit()
```

C types map directly: `uint32` ↔ `uint32_t`, `*byte` ↔ `void*`/`char*`, `int32` ↔ `int32_t`. `str` auto-coerces to `*byte` for C calls, and `*byte` auto-coerces to `str` on return. No manual casting.

Compile with `-lSDL3` and the linker resolves everything:

```bash
mix sdl3_window.mix -o sdl3 -lSDL3
```

#### Path 2: Zero-bind `use c` — auto-generate from headers at compile time

For larger C libraries, write one line and MIX generates all the bindings automatically during compilation — no `--bind` step required:

```rust
use c "SDL3/SDL.h" link "SDL3"

main()
    SDL_Init(SDL_INIT_VIDEO)
    defer SDL_Quit()

    win = SDL_CreateWindow("MIX + SDL3", 800, 600, 0)
    defer SDL_DestroyWindow(win)

    event = SDL_Event()                      // SDL structs become MIX shapes
    running! = true

    while running
        while SDL_PollEvent(event) != 0
            if event.type_ == SDL_EVENT_QUIT // C struct fields directly accessible
                running! = false

        SDL_SetRenderDrawColor(rnd, 100, 149, 237, 255)
        SDL_RenderClear(rnd)
        SDL_RenderPresent(rnd)
        SDL_Delay(16)
```

This single line:

```rust
use c "SDL3/SDL.h" link "SDL3"
```

does the following at compile time:
1. Runs the C preprocessor on the header (resolves `#include`s, macros, `#define` constants)
2. Parses every function prototype into MIX `extern` declarations
3. Converts C `struct`/`union` types into MIX `shape`/`union` definitions
4. Extracts integer and float `#define` constants as `@const` values
5. Filters out system headers — only user-relevant declarations come through
6. Feeds everything into the compiler as if you'd written it by hand

C structs become MIX shapes with named fields, so `SDL_Event`'s `type` field (which conflicts with the MIX keyword `type`) is automatically renamed to `type_`. Union members are all accessible at offset 0, matching C semantics.

SDL3, OpenGL, libc — all work the same way. There is zero glue code between MIX and C.

#### Optional: `mix --bind` for reusable binding files

When you want a standalone `.mix` bindings file (for version control, sharing across projects, or offline use), run:

```bash
mix --bind SDL3/SDL.h --lib SDL3 -o sdl3.mix
```

This produces a `.mix` file with all the `extern` declarations, `shape` definitions, and `@const` constants. Import it with `use sdl3` like any MIX module. The generated file is valid MIX source — readable, editable, and auditable.

#### Real-world: SDL3 window with OpenGL

MIX can drive OpenGL directly through C interop — declaring only the GL functions the program needs, not importing the entire GL header:

```rust
extern "SDL3"
    SDL_Init(flags: uint32) -> bool ~
    SDL_CreateWindow(title: *byte, w: int32, h: int32, flags: uint64) -> *byte ~
    SDL_GL_CreateContext(win: *byte) -> *byte ~
    SDL_GL_SwapWindow(win: *byte) ~

extern "GL"
    glClearColor(r: float32, g: float32, b: float32, a: float32) ~
    glClear(mask: uint32) ~
    glDrawArrays(mode: uint32, first: int32, count: int32) ~

main()
    SDL_Init(SDL_INIT_VIDEO)
    win = SDL_CreateWindow("MIX Triangle", 800, 600, SDL_WINDOW_OPENGL)
    ctx = SDL_GL_CreateContext(win)

    glClearColor(0.1, 0.1, 0.1, 1.0)

    running! = true
    while running
        glClear(GL_COLOR_BUFFER_BIT)
        glDrawArrays(GL_TRIANGLES, 0, 3)
        SDL_GL_SwapWindow(win)
```

#### How it works inside the compiler

The `cbind` module (`src/cbind.c`, ~2,000 lines) is a self-contained C header parser that MIX built into the compiler binary. When the compiler encounters a `use c "header.h"` declaration, it:

1. Locates the header via standard include paths and `lib/vendor/` directories
2. Runs `cc -E` (the system C preprocessor) to expand macros and resolve includes
3. Parses the preprocessed output — extracting function signatures, struct/unions, typedefs, and `#define` constants
4. Maps C types to MIX types (`int` → `int32`, `double` → `float`, `char*` → `*byte`, etc.)
5. Strips qualifiers (`const`, `volatile`, `__restrict`, `__attribute__`)
6. Generates MIX source and feeds it through the same lexer → parser → sema pipeline

Everything happens in a single `mix run` command. No build scripts, no code generation step, no makefile rules.

## The Compiler Pipeline

### Lexer

The lexer walks source text character-by-character, emitting tokens. MIX uses indentation-sensitive syntax (INDENT/DEDENT tokens like Python) instead of braces or `begin`/`end`:

```c
// token.h
typedef enum {
    TOK_INT_LIT, TOK_FLOAT_LIT, TOK_STR_LIT,
    TOK_IDENT, TOK_MUT_IDENT,           // x vs x!
    TOK_INDENT, TOK_DEDENT, TOK_NEWLINE,
    TOK_PLUS, TOK_MINUS, TOK_STAR, TOK_SLASH,
    TOK_EQ, TOK_EQ_EQ, TOK_BANG_EQ,
    TOK_LT, TOK_GT, TOK_LT_EQ, TOK_GT_EQ,
    TOK_IF, TOK_ELSE, TOK_WHILE, TOK_FOR,
    TOK_FN, TOK_DONE, TOK_FAIL,
    TOK_SHAPE, TOK_UNION, TOK_MATCH,
    TOK_GO, TOK_WAIT, TOK_SHARED,
    TOK_ZONE, TOK_DEFER,
    TOK_USE, TOK_PUB, TOK_EXTERN,
    TOK_AT_CONST, TOK_AT_OS, TOK_AT_ARCH,
    // ... ~60 token types total
} TokenKind;
```

The lexer handles:
- Indentation tracking (INDENT/DEDENT tokens at line beginnings)
- `x!` as a mutable identifier token (TOK_MUT_IDENT)
- `//` comments
- String interpolation parsing (`"Hello {name}!"` → concatenation nodes)

### Parser

A **recursive descent parser** with **Pratt parsing** for expressions. Each grammar rule is a function that calls into sub-rules recursively:

```c
// parser.c
static AstNode *parse_expr_prec(Parser *p, Precedence min_prec) {
    AstNode *left = parse_prefix(p);
    while (p->cur->kind != TOK_EOF &&
           get_precedence(p->cur->kind) > min_prec) {
        left = parse_infix(p, left);
    }
    return left;
}
```

The parser produces an AST with arena allocation — no memory tracking, no lifetimes, just a flat arena that's destroyed after compilation.

### Semantic Analysis

The semantic analyzer walks the AST and:
- Resolves names to declarations (scoped symbol table)
- Infers and checks types
- Validates mutation safety (`!` on mutable targets only)
- Monomorphizes generic functions per concrete type
- Registers `pub` symbols for cross-module visibility
- Warns on non-exhaustive `match` arms
- Auto-wraps return types for `~` functions containing `fail` or `?`

```c
// sema.c — type inference
static MixType *infer_type(Sema *s, AstNode *expr) {
    switch (expr->kind) {
        case NODE_INT_LIT:
            return type_int();
        case NODE_FLOAT_LIT:
            return type_float();
        case NODE_STR_LIT:
            return type_str();
        case NODE_BINARY: {
            MixType *lt = infer_type(s, expr->binary.left);
            MixType *rt = infer_type(s, expr->binary.right);
            // Unify or widen (int + float → float)
            return unify_types(lt, rt);
        }
        // ...
    }
}
```

### Lowering

Before code generation, the AST is lowered into a compact **LIR** (Lowered IR) that makes shape copies, field addresses, and control flow explicit. This layer is shared between the LLVM and C backends, so language semantics are decided once rather than duplicated.

```c
// lir.h
typedef enum {
    LIR_ALLOCA,      // local variable slot
    LIR_LOAD,        // load from slot or memory
    LIR_STORE,       // store to slot or memory
    LIR_MEMCPY,      // whole-shape copy
    LIR_FIELD_ADDR,  // compute field address within a shape
    LIR_CALL,        // function call
    LIR_BRANCH,      // conditional branch
    LIR_JUMP,        // unconditional jump
    LIR_RETURN,      // function return
    // ...
} LirOpKind;
```

### LLVM Backend

The LLVM backend emits textual `.ll` IR and shells out to `clang -c` to produce object files. The emitted IR uses the host target triple — no hardcoded architecture assumptions:

```c
// llvm_emit.c
void llvm_emit_function(LlvmEmitter *e, LirFunction *fn) {
    fprintf(e->out, "define %s @%s(", 
            type_to_llvm(fn->return_type), fn->name);
    for (int i = 0; i < fn->param_count; i++) {
        fprintf(e->out, "%s %%p_%s",
                type_to_llvm(fn->params[i].type), fn->params[i].name);
        if (i < fn->param_count - 1) fprintf(e->out, ", ");
    }
    fprintf(e->out, ") {\n");
    // Emit body...
}
```

The LLVM backend supports DWARF debug info (`--debug` flag for source-level lldb debugging).

### C Backend

The C backend emits portable C code that can be compiled with any standard C compiler. It's used as a portability fallback for platforms without LLVM.

## Tooling

Beyond the compiler itself, MIX ships with a surprising amount of tooling:

### LSP Server

`mix-lsp` provides IDE features: diagnostics, hover type info, go-to-definition, find references, document/workspace symbols, rename, inlay hints, code actions, signature help, and completion. It works with Neovim (built-in plugin) and VSCode (extension).

### Code Formatter

`mix fmt` is a token-based formatter that preserves comments. It supports `--check` (CI mode: exit 1 on diffs), `--diff` (unified diff), `-w` (write in place), and recursive directory walk.

### C Header Binding Generator

`mix --bind header.h --lib SDL3` generates MIX bindings from C headers automatically. It runs the preprocessor, extracts function prototypes and `#define` constants, maps C types to MIX types, and produces a valid `.mix` file.

```bash
mix --bind /opt/homebrew/include/SDL3/SDL.h --lib SDL3 -o sdl3.mix
```

### Build System

`build.mix` files allow declarative project builds:

```rust
main() ~
    app = Project(
        name: "game",
        entry: "src/game.mix",
        output: "build/game",
        libs: ["SDL3", "m"],
        lib_paths: ["/opt/homebrew/lib"]
    )
    app.build()
```

## The AI Pair-Programming Experience

This is the heart of the project. MIX wasn't built in a vacuum — it was built with AI as a constant collaborator. Here's what that looked like in practice:

### How We Worked

1. **I described the goal** — "I want MIX to have generic functions with type parameters. Something like `@T` before a function name."
2. **AI explained the approaches** — "There are a few strategies: monomorphization (generate a copy per concrete type), type-erased representation (store everything as 64-bit values), or JIT compilation. For a systems language, monomorphization gives the best codegen..."
3. **I chose the approach** — Monomorphization, because MIX targets native performance.
4. **AI generated the code** — Sema pass for collecting type arguments, cloning function bodies with substitutions, QBE emitter for per-type dispatch.
5. **I reviewed every line** — Understanding each change, asking for clarifications, catching mismatches with the existing codebase.
6. **We debugged together** — When generic functions produced wrong results for float types, I pasted the test output and AI traced through the generated QBE IR to find the ABI mismatch in how floats were passed.

This workflow was transformative. I wasn't consuming tutorials — I was directing the construction of something real, and AI was the senior engineer implementing my specifications, catching mistakes, explaining concepts, and helping me level up.

### What AI Was Good At

- **Explaining concepts from first principles** — "Here's why monomorphization generates more code but runs faster than type erasure."
- **Debugging generated code** — Tracing through emitted QBE/LLVM IR to find ABI mismatches, wrong type suffixes, or misaligned struct layouts.
- **Generating complete, working passes** — The lexer, parser, sema, and both backends were all AI-generated based on my descriptions of the language.
- **Suggesting test cases** — "You should test what happens when a generic function is called with both int and float in the same program."

### What I Had to Learn Myself

- **Debugging codegen bugs** — AI can generate a parser, but it can't feel the frustration of a segfault caused by a wrong struct offset in the C backend. I had to learn to read generated code.
- **Language design taste** — Should `else if` be one keyword or two? Should `main()` have implicit `~`? These are judgment calls AI can't make.
- **When to simplify** — AI would sometimes generate overly complex solutions. Learning to say "this can be simpler" was a skill I developed over time.
- **Understanding the generated code well enough to review it** — The day I caught a wrong load suffix in the QBE emitter before running the tests was the day I knew I was actually learning.

## What I Learned

Building MIX fundamentally changed how I think about software:

1. **Compilers aren't magic.** After directing the construction of MIX, I can look at any language feature and have a reasonable guess at how it's implemented under the hood. When I write a generic function in another language, I can picture the monomorphization pass. When I use a closure, I can imagine the heap-allocated environment frame.

2. **AI as a teaching tool is transformative.** I learned more about compilers in the time it took to build MIX than I did in years of reading textbooks. The difference is *building* — when you have to make something work, you truly understand it.

3. **Start simple, then extend.** MIX started with arithmetic expressions and basic functions. Shapes, generics, concurrency, and the LSP came later, one at a time. I never would have finished if I'd tried to design everything upfront.

4. **Error messages matter.** Spending time on good error reporting — source locations, colored output, descriptive messages — made debugging dramatically easier. Every hour spent on error messages saved three hours of debugging.
